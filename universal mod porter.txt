# 2. Nguyên tắc kiến trúc bắt buộc

### 2.1. Architecture First, Implementation Second

Trước khi triển khai bất kỳ module quan trọng nào:

- Phân tích yêu cầu.
- Thiết kế kiến trúc.
- Xác định interface.
- Xác định dependencies.
- Xác định luồng dữ liệu.
- Xác định lỗi có thể xảy ra.
- Xác định phương pháp kiểm thử.
- Viết tài liệu kỹ thuật.

Không được bắt đầu code một cách tùy tiện rồi mới tìm cách ghép các module lại với nhau.

Tuy nhiên, không được dành quá nhiều thời gian xây dựng kiến trúc lý thuyết. Mỗi thiết kế phải phục vụ một nhu cầu cụ thể và có kế hoạch kiểm chứng.

### 2.2. Modular Monolith First

Ưu tiên kiến trúc Modular Monolith trong các phiên bản đầu.

Không chia thành Microservices ngay từ đầu nếu chưa có nhu cầu thực tế.

Core Engine phải được chia thành các module độc lập, có interface rõ ràng và không phụ thuộc trực tiếp vào implementation nội bộ của module khác.

Khi cần mở rộng thành server hoặc cloud service, có thể tách module thành service độc lập mà không phải viết lại toàn bộ nghiệp vụ.

### 2.3. Loose Coupling, High Cohesion

- Giảm phụ thuộc trực tiếp giữa các module.
- Mỗi module có một trách nhiệm rõ ràng.
- Không để GUI chứa migration logic.
- Không để AI Provider phụ thuộc trực tiếp vào GUI.
- Không để từng mod loader tự triển khai lại những chức năng chung.
- Sử dụng interface, dependency injection và adapter khi phù hợp.

### 2.4. Extensibility by Design

UMMP phải có khả năng bổ sung:

- Minecraft versions.
- Mod loaders.
- Server platforms.
- Programming languages.
- Build systems.
- Decompilers.
- Mapping providers.
- Bytecode transformers.
- AI providers.
- Rendering technologies.
- Networking technologies.
- Native toolchains.
- Migration recipes.
- Testing frameworks.

Không được giả định rằng danh sách công nghệ hiện tại là đầy đủ.

### 2.5. Evidence-Based Development

Không đánh dấu một module là hoàn thành chỉ vì source code đã được tạo.

Mỗi chức năng phải có bằng chứng:

- Unit tests.
- Integration tests.
- Build results.
- Validation results.
- Documentation.
- Known limitations.

# 3. Các kiến trúc phải đánh giá và bổ sung

Hãy phân tích các kiến trúc sau, xác định kiến trúc nào cần thiết, nên triển khai ở giai đoạn nào và vì sao.

Không bắt buộc áp dụng tất cả. Phải đánh giá dựa trên lợi ích thực tế, chi phí và độ phức tạp.

## 3.1. Core Software Architecture

- Modular Monolith.
- Layered Architecture.
- Hexagonal Architecture.
- Clean Architecture.
- Domain-Driven Design.
- Dependency Injection.
- Interface-Based Design.

Mục tiêu: Core Engine không bị phụ thuộc vào GUI, AI provider, Minecraft loader hoặc công cụ build cụ thể.

## 3.2. Plugin & Adapter Architecture

Thiết kế một hệ thống cho phép thêm công nghệ mới mà không sửa toàn bộ Core.

Cần có:

- Plugin SDK.
- Plugin API.
- Plugin Registry.
- Plugin Loader.
- Plugin Lifecycle.
- Plugin Dependency Manager.
- Plugin Versioning.
- Capability Discovery.
- Compatibility Validation.
- Permission System.
- Sandboxing.
- Plugin Configuration.

Phân biệt:
- Adapter: chuyển đổi giữa các hệ thống hoặc API.
- Plugin: mở rộng chức năng của ứng dụng.
- Migration Recipe: quy tắc chuyển đổi có thể tái sử dụng.
- Provider: triển khai một dịch vụ cụ thể như AI, mapping hoặc decompiler.

## 3.3. Migration Pipeline Architecture

Thiết kế pipeline có các bước độc lập:

Import → Detect → Analyze → Plan → Transform → Build → Test → Review → Export.

Mỗi bước phải:

- Có input/output rõ ràng.
- Có trạng thái thực thi.
- Có log.
- Có timeout.
- Có retry policy phù hợp.
- Có error handling.
- Có checkpoint.
- Có thể chạy lại khi thất bại.
- Không làm hỏng kết quả của các bước trước.

Hỗ trợ dependency graph để xác định thứ tự chạy.

# 6. Quản lý quan hệ phụ thuộc

Tạo Dependency Graph cho toàn bộ dự án.

Phải chỉ rõ:

- Module nào cần hoàn thành trước.
- Module nào có thể phát triển song song.
- Module nào cần interface trước khi implementation.
- Module nào có thể thay thế.
- Module nào có rủi ro phụ thuộc công nghệ bên ngoài.

Không tạo dependency vòng.

Ưu tiên các dependency direction:

Presentation → Application → Domain

Infrastructure → Application/Domain abstractions

Domain không được phụ thuộc vào GUI, database cụ thể, AI provider hoặc Minecraft loader implementation.

Migration adapters phải phụ thuộc vào các contract chung, không phụ thuộc lẫn nhau nếu không có lý do rõ ràng.

Hãy xác định các điểm cần dùng:
- Dependency Injection.
- Event Bus.
- Message Queue nếu thực sự cần.
- Plugin Registry.
- Service Interface.
- Repository Pattern.
- Adapter Pattern.
- Strategy Pattern.
- Factory Pattern.
- Command Pattern.

Giải thích lý do dùng từng pattern, tránh áp dụng pattern chỉ để làm kiến trúc phức tạp hơn.

# 9. Quy trình phát triển theo milestone

Mỗi milestone phải tuân theo quy trình:

1. Kiểm tra trạng thái repository.
2. Đọc tài liệu kiến trúc hiện tại.
3. Kiểm tra dependencies.
4. Xác định phạm vi thay đổi.
5. Tạo Git branch.
6. Tạo backup/checkpoint khi thay đổi lớn.
7. Viết hoặc cập nhật tests.
8. Triển khai code.
9. Chạy tests.
10. Chạy build.
11. Review diff.
12. Cập nhật tài liệu.
13. Cập nhật roadmap.
14. Tạo Git commit.
15. Chỉ chuyển milestone tiếp theo khi đạt acceptance criteria.

Nếu test thất bại:
- Phân tích nguyên nhân.
- Không che giấu lỗi.
- Không tự ý bỏ qua test.
- Không đánh dấu milestone hoàn thành.
- Có thể tiếp tục những task độc lập nếu không ảnh hưởng tính đúng đắn.

# 11. Quản lý rủi ro

Tạo Risk Register, tối thiểu bao gồm:

- Minecraft API thay đổi lớn giữa phiên bản.
- Thiếu source code.
- JAR bị obfuscate.
- Mapping không đầy đủ.
- Mixin phức tạp.
- Rendering pipeline thay đổi.
- Native dependency không tương thích.
- Thiếu tài liệu cho mod loader cũ.
- Mod có custom classloader.
- Dependency không còn tồn tại.
- AI sửa sai logic.
- AI tạo regression.
- Chi phí API cao.
- Sandbox không đủ an toàn.
- Mod không thể kiểm thử tự động.
- Khác biệt giữa client và server.
- License không cho phép redistribution.

Mỗi rủi ro cần:
- Probability.
- Impact.
- Severity.
- Mitigation.
- Fallback.
- Owner.

# 12. Nguyên tắc tránh overengineering

Đây là yêu cầu quan trọng.

Không được:

- Triển khai microservices khi chưa cần.
- Dùng quá nhiều database.
- Tạo quá nhiều abstraction không có use case.
- Xây dựng plugin marketplace trước khi Plugin SDK ổn định.
- Tạo hệ thống AI nhiều Agent quá phức tạp ngay từ MVP.
- Tích hợp mọi ngôn ngữ cùng lúc.
- Hỗ trợ mọi phiên bản ngay trong bản đầu tiên.
- Tạo framework riêng nếu đã có thư viện phù hợp.
- Viết lại những công cụ open-source đang hoạt động tốt mà có thể tích hợp hợp pháp.

Mỗi kiến trúc phải trả lời được:
1. Nó giải quyết vấn đề gì?
2. Vì sao cần nó?
3. Có thể triển khai ở giai đoạn nào?
4. Chi phí bảo trì là gì?
5. Có giải pháp đơn giản hơn không?

Ưu tiên kiến trúc tối thiểu có thể mở rộng, không phải kiến trúc phức tạp nhất.
